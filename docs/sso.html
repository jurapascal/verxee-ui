Hub & single sign-on

One sign-in for a whole family of apps: people sign in once in the hub (e.g. alba-rosa.cz/hub), the hub shows each app in an iframe, and every app signs them in silently. Outside the hub the same apps offer Sign in with Alba Rosa Hub and Sign in with Google.

How it fits together. The hub is an OpenID Connect provider. Each app is an OIDC client with its own client_id/secret, keeps its own users and roles, and only learns who the person is (verified e-mail + stable sub) from the hub or from Google. Google is just another OIDC provider, so one library handles both.

The pieces

Flow

  1. Inside the hub. The hub frames /app/. The app has no session → it redirects inside the frame to auth.php?provider=hub&prompt=none → hub sees its own session → returns a code at once (no screen) → auth.php verifies, starts the app session, sends the frame back to where it was with ?vx_sso=ok.
  2. Not signed in at the hub (or the silent try fails): the app gets ?vx_sso=fail, shows its sign-in screen with only the hub button, and posts login-required to the hub. The hub signs the person in at the top level (Google cannot run inside iframes) and reloads the frame — step 1 now succeeds.
  3. Outside the hub (app opened directly): the sign-in screen shows Sign in with Alba Rosa Hub and Sign in with Google (plus the password form if you keep it). One click, normal OIDC redirect.
  4. Sign-out. Signing out in the app posts logout to the hub (the hub decides whether to end the hub session too). Sign out everywhere in the hub posts logout to every frame; each app ends its own session.

VerxeeUI.app({
  hub: { origin: 'https://alba-rosa.cz' },     // hubs allowed to frame and talk to this app (string or array)
  auth: {
    urls: { session: 'auth.php?me=1', logout: 'auth.php?logout=1' },
    providers: ['hub', 'google'],              // buttons on the sign-in screen
    ssoUrl: 'auth.php?provider={id}',          // default; return= and prompt=none are appended
    password: false,                           // hide the e-mail + password form (SSO only)
    sso: { provider: 'hub', auto: 'embedded' } // silent sign-in: 'embedded' (only in a frame, default), true (always), false
  },
  …
});

Browser: plain PHP pages (no app())

Server-rendered apps only need the bridge — include verxee-ui.js and:

VerxeeUI.hub.connect({ origin: 'https://alba-rosa.cz', topbar: 'keep', logoutUrl: 'auth.php?logout=1' });
VerxeeUI.hub.setTitle('Orders');      // shown in the hub's tab/title
VerxeeUI.hub.setBadge(3);             // unread count next to the app in the hub
VerxeeUI.hub.on('navigate', m => …); // any hub message
VerxeeUI.hub.embedded;                // true once the hub answered

Silent sign-in for such apps is a server redirect: if there is no session and the request is a page load, redirect to auth.php?provider=hub&prompt=none&return=… once (remember the attempt in the session to avoid loops).

Message protocol

All messages are objects { vx: 1, type, … } sent with an explicit target origin. Both sides check event.origin against their allowlist and event.source against the expected window; anything else is ignored.

DirectiontypeFields
app → hubreadytitle, url — sent on start
app → hubusername, email — after sign-in
app → hubtitle · route · badgetitle · url · count
app → hublogin-required— app has no session and silent sign-in did not help
app → hublogout— person signed out in the app
hub → apphello · themetheme: 'light' | 'dark'
hub → applogout— end the app session
hub → appnavigateurl — same-origin only

Server: VerxeeSso

require 'server/php/VerxeeSso.php';
VerxeeSso::sessionStart('MYAPPSESS');                 // Lax, HttpOnly, Secure on HTTPS, strict mode
$sso = new VerxeeSso(require 'sso.config.php');       // providers, redirect_uri, optional allowlists

// start
header('Location: ' . $sso->start('hub', ['return' => $_GET['return'] ?? '/', 'prompt' => $_GET['prompt'] ?? null]), true, 303);

// callback
try { $id = $sso->finish($_GET); }                    // provider, sub, email, name, picture, roles, return
catch (VerxeeSsoError $e) {
  if ($e->reason === 'login_required') { header('Location: ' . VerxeeSso::withResult($e->returnTo, 'fail')); exit; }
  // show $e->getMessage()
}
$user = find_user_by_email($id['email']);             // YOUR users table decides access and roles
VerxeeSso::login($user);                               // new session id, then store
header('Location: ' . VerxeeSso::withResult($id['return'], 'ok'), true, 303);

Checked for you: issuer (incl. discovery), aud/azp, RS256 signature by kid (re-fetches keys once on rotation), exp/iat with leeway, nonce, single-use state (10 min), PKCE S256, verified e-mail, Google Workspace hd, optional allowed_domains/allowed_emails, local-only return paths. php tests/sso/run.php runs the flows against a fake provider.

Cookies, headers and iframes

  • Same site as the hub (alba-rosa.cz/app in alba-rosa.cz/hub): session cookie SameSite=Lax — the default of sessionStart(). Not Strict: the return from the provider is a cross-site navigation and a Strict cookie would not be sent, so state would be lost.
  • Another site (accom.ubysys.tech in the hub): VerxeeSso::sessionStart('NAME', crossSiteFrame: true) → SameSite=None; Secure; Partitioned. The session then lives only inside the hub's frame (a separate one when opened directly). Prefer moving such apps under the hub's site when possible.
  • Framing: send Content-Security-Policy: frame-ancestors 'self' https://alba-rosa.cz (and drop X-Frame-Options: DENY) from every app that lives in the hub. Without it the hub cannot show the app; with * anyone could frame it (clickjacking).
  • The hub's own sign-in page must not be framable (frame-ancestors 'none'), and its authorize endpoint must redirect at once for prompt=none (never render a page in someone's frame).

What the hub must provide

  • OIDC discovery at {issuer}/.well-known/openid-configuration, authorize (code flow, PKCE S256 required, prompt=none → login_required), token (client_secret_basic), jwks (RS256), optionally end_session.
  • Registered clients with exact redirect_uri match, one per app; secrets stored hashed.
  • id_token claims: sub (stable per person), email, email_verified, name, optionally roles for that client.
  • The frame side: hello/theme on load, handle login-required (top-level sign-in, then reload that frame once), logout, title/badge.
