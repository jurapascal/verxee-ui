Security

What Verxee UI does for you in the browser, and what only your server can do.

Threat model in one paragraph

Everything that runs in the browser is under the visitor's control. So the UI can make attacks harder (XSS, CSRF, clickjacking, session theft) and make the secure path the easy one — but authentication, sessions, authorisation and rate limiting live on the server. Never ship data in the HTML or JS that a signed-out user must not see, and re-check permissions on every API call.

Built into the UI

ProtectionHow
XSS: text is textEvery label, title, message and cell is set with textContent. User data in text / label options can't inject markup.
XSS: HTML is sanitizedThe html options (html block, modal/popover html, card html) pass through VerxeeUI.sanitize(): scripts, iframes, on* handlers, javascript:/data: URLs are removed. Opt out only deliberately: configure({ security: { trustHtml: true } }).
Unsafe URLsEvery href/logo goes through safeHref — javascript:, vbscript: and data: become #.
CSP-friendlyNo eval, no inline event handlers, no inline <script>/<style>. Works under script-src 'self'; style-src 'self' (tested). Self-hosted fonts and icons need no third-party origins.
CSRFVerxeeUI.fetch adds the token header to unsafe methods and uses same-origin credentials.
No secrets in storageThe framework never stores tokens or passwords. Only the theme choice lives in localStorage.
No user enumerationOne generic sign-in error; the reset screen always says “if an account exists…”.
Session hygieneIdle sign-out, sign-out in all tabs, content removed from the DOM on sign-out, 401 handling.
Supply chainCoreUI, icons and fonts are self-hosted/vendored. For CDN use, Subresource Integrity hashes are published in dist/sri.json (see Installation).

What your server must do

examples/server.mjs is a small reference implementation (about 100 lines, no dependencies) of exactly these points:

  1. Cookies, not tokens in JS. Session id in a cookie that is HttpOnly; Secure; SameSite=Strict, 256-bit random, stored hashed server-side, regenerated on login, destroyed on logout, with idle and absolute expiry.
  2. Hash passwords with scrypt / argon2 / bcrypt; compare in constant time; do the work even for unknown users.
  3. Rate-limit and lock out per account and per IP; return 429. (The UI cool-down is cosmetic.)
  4. CSRF protection on every state-changing request (double-submit cookie or synchroniser token) — plus SameSite.
  5. Authorise every request against the session's permissions; the UI's can filter is not access control.
  6. Security headers on every response: a strict CSP, X-Content-Type-Options: nosniff, frame-ancestors 'none' (clickjacking), Referrer-Policy, HSTS over HTTPS.
  7. Use HTTPS only. Add 2FA for admin accounts (the UI supports the code step).
  8. Escape output and validate input on the server as well.

Recommended CSP

Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; font-src 'self'; connect-src 'self';
  frame-ancestors 'none'; base-uri 'self'; form-action 'self'

Load the runtime as a normal file (<script src="…/verxee-ui.min.js">) and put your VerxeeUI.app({…}) call in a file too, not inline (examples/auth.js). If you serve it from a CDN, add that origin to script-src and use the SRI hash.

Checklist before going live

  • ☐ HTTPS everywhere, cookies Secure; HttpOnly; SameSite
  • ☐ Every API route checks the session and the permission
  • ☐ Login is rate-limited; passwords hashed with a slow hash
  • ☐ CSRF token verified on POST/PUT/PATCH/DELETE
  • ☐ Strict CSP and the headers above
  • ☐ Nothing confidential in static HTML/JS; data is fetched after sign-in
  • ☐ trustHtml is still false; user data goes in text/label, never html
  • ☐ Pin the version (@v2.3.0) and use SRI

Reporting a vulnerability

Please report security issues privately through GitHub's “Report a vulnerability” on the repository rather than a public issue.
